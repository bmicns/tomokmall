## 1. 1련암거 — 운영 DB 수정 없이 검색 정확도 개선

**발견한 문제(수정 전)**: 운영 1련암거 10개는 상품명이 규격 코드뿐(`1.0*1.0*2.0_130T*130T_구`)이고 품목 이름 '암거'는 분류에만 있어,
AI 검색에서 '암거'·'1련암거'가 **0건**, '박스 암거 폭 1000'은 이름이 비슷한 PE전원박스로 안내됐다. 규격 칸에 '규격:'이 없어 폭·길이 조건으로도 걸러지지 않았다.

| 수정 | 내용 |
|---|---|
| 분류 이름으로 찾기 | 검색어가 분류 이름에 있고, 그 분류 상품이 글자 검색(상품명·규격·설명)에 안 잡히며 상품명이 규격 코드뿐일 때만 후보로 더함 — 일반 검색은 그대로(25종·통행 12종 결과 글자까지 같음) |
| 상품명 규격 코드 | 등록 규격이 없을 때만 상품명 앞의 치수 코드(`1.0*0.8*2.0_130T*130T`, 뜻 모르는 `_구`는 뺌)를 '규격 표기에 그 숫자가 있음' 근거로 사용. 소수 표기는 m(1.0 = 1000mm), 두께 `130T`는 m 로 보지 않음. **숫자 자리의 뜻(폭·높이·길이)은 확인되지 않았으므로 항상 '규격 확인 필요'** — 확인된 폭이라고 하지 않음 |
| 잘못 걸림 방지 | 중량 `2,900kg` 의 900 이 폭 900 에 걸리던 문제 — 규격 코드가 있는 상품은 코드만 본다 |
| 표시 | 카드 규격 줄 = 품목(분류) 이름 '1련암거', 판매 단위 `중량/단위: 2,900kg / 본` → '본'(이전엔 '2,900kg / 본') |
| 하중 | 암거는 차량 통행에서 하중 근거가 없어 '하중 확인 필요'(상품명엔 '암거'가 없어 분류 이름으로 판정 — 영향받는 상품은 1련암거 10개뿐, 운영 구조 DB 로 확인) |

결과(로컬 운영 구조 DB): '암거' → 1련암거 10개 · '암거 폭 1000' → 코드에 1.0 이 있는 5개(규격 확인 필요) · '폭 900' → 없음 안내 · '폭 1.2m' → 1.2 코드 2개 · 대형차 → 모두 하중 확인 필요.
수량: 1본 길이가 확인되지 않아 설치 길이로 수량을 계산하지 않는다(코드의 2.0·3.0 이 길이인지 미확인).
테스트 환경: `scripts/testdb/prodlike-db.php` 가 `data/dacity`(운영 1련암거 출처)도 운영 분류에 붙여 넣도록 보강 → 로컬 상품 1,407개(이전 1,397 + 10).
남은 DB 후보(4차 보고와 같음, 실행 안 함): 규격 칸에 크기 넣기·단위/중량 칸 채우기·사람 확인 뒤 이름표 — 하면 '확인 필요'가 '확인됨'으로 바뀌고 수량 계산 가능.

## 3. 모호한 자연어 표현 확대

| 표현 | 처리 |
|---|---|
| '1m짜리 그레이팅'·'2미터짜리 수로관' | 제품 1개 길이(품목 3m·관 6m 이하) |
| '10미터짜리 그레이팅' | 1개 길이로 너무 김 → 길이 조건 없이 확인 |
| '20m 정도 깔 거야'·'대략 30미터 정도 필요' | 설치 총 길이('정도·쯤·가량' 허용) — 앞 표가 있으면 그 제품으로 수량 |
| '50센치짜리 그레이팅'·'300짜리' | 치수 이름 없는 숫자(cm 는 ×10) → 폭으로 단정하지 않고 spec_mm + 어느 치수인지 확인 |
| '폭 30'(단위 없음, 100 미만) | 30mm 인지 30cm 인지 확인 — GPT 가 넣은 폭(30·300)도 뺌 |
| '폭 40센치 길이 1미터' | 폭 400·제품 길이 1000(폭과 붙인 길이 — '센치' 단위 인식 보강) |
| '길이를 1.5배로'·'폭을 반으로' | 바꿀 값이 하나로 정해지면 계산(소수 배율 허용) |
| '좀 더 넓은 거'·'조금 더 짧은 걸로' | 얼마나 바꿀지 없음 → 앞 조건 유지(GPT 가 임의로 정한 값 되돌림) + 원하는 치수 확인 |
| '차는 가끔 다녀요'·'차가 거의 안 다녀요' | 차량(가끔이라도 다니면 안전 쪽) |
| '사람이랑 자전거만 다녀요' | 보행자 |
| '아까 그거 다시 보여줘'·'제외했던 거 다시 보여줘' | 고객이 앞서 뺀 제품 제외를 이어 가지 않음(최신 요청 우선). '다시 추천'(다른 제품)은 해당 없음 |
| '높이 50짜리'·'직경 600 맨홀뚜껑'·'두께 80T' | 폭·길이로 만들지 않음(그대로) |

## 4. `member_price_display` 일시 실패 — 원인 확인·재현·조치

**원인(재현함)**: 로컬 테스트 DB 컨테이너가 **비정상 종료**되면(세션 시간 제한으로 Docker 데몬이 꺼짐 — 4차·5차 시작 때 모두 그 직후 첫 실행에서 실패) InnoDB FULLTEXT 색인이 표와 어긋나,
그 뒤 넣은 행이 FULLTEXT 검색에 안 나오거나 **일부만** 나온다. `search_products()` 는 FULLTEXT 결과가 **0건일 때만** LIKE 로 넘어가므로, 일부만 나오면 나머지 상품이 빠진다.
테스트가 넣은 목 상품 4개 중 '상품 4' 하나만 검색된 상태를 재현했다(`FULLTEXT 1 / LIKE 4`) — 그래서 '상품 1' 금액 단언 4개가 실패. 원인은 DB 색인 상태(SQL `MATCH` 건수로 직접 확인)이고 `search_products()` 는 이번 작업들에서 바꾸지 않았으므로 코드 변경과 무관.
깨끗한 재시작(`docker restart`) 뒤에는 재현되지 않고, `OPTIMIZE` 만으로는 복구되지 않으며, **표 다시 만들기(`ALTER TABLE … ENGINE=InnoDB`)로 복구**된다.

조치(테스트 환경만, 운영 코드 그대로):
- `tests/member_price_display.test.php`: 목 상품을 넣은 직후 FULLTEXT 로 모두 찾히는지 점검 — 아니면 '환경 오류(코드 오류 아님)'와 복구 명령을 알리고 종료 코드 2(코드 실패와 구분).
- `scripts/testdb/fts-rebuild.sh`: 테스트 컨테이너의 *_test DB 만 점검·재생성(`--force` 는 바로 재생성). 비정상 종료 뒤 한 번 실행.

운영 점검(읽기 전용): 그레이팅·수로관·경계석·흄관·맨홀·보도블록·이중벽관 7개 말로 FULLTEXT 건수 = LIKE 건수(138=138, 198=198 …) — **운영 색인은 정상**.
제안(실행 안 함): 운영 DB 가 비정상 종료되면 같은 현상으로 사이트·AI 검색에서 새 상품이 빠질 수 있다 — 장애 뒤 점검 항목으로 위 건수 대조를 넣거나,
`search_products()` 가 FULLTEXT 결과를 LIKE 건수와 비교하는 보완은 사이트 검색 전체에 영향이 있어 별도 요청 시 검토.
