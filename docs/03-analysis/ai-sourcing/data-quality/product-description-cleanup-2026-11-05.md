> 요청: "상품 설명도 같이 정비해주세요"(2026-11-05). 운영 반영은 보류 지시에 따라 **파일만 만들었다**(운영 DB 변경 없음).
> **검토 상태(2026-11-05)**: 사용자가 검토표를 검토했다("상품 설명 검토표 검토했습니다"). 뺄 상품 요청은 없었다. 운영 적용(`50`·`51`)은 계속 보류 — 운영 배포·DB 변경은 따로 승인 후(5장 순서).

## 1. 대상과 자료

- 운영 활성 상품 1,341개 중 설명(`products.description`)이 있는 상품 691개. 2026-11-05 원격 관리 API 읽기 전용 조회(`id, category_id, name, spec, description` / 분류 `id, parent_id, name, description`). 가격 칸은 조회하지 않았다.
- 점검 결과(`../explanation-data-2026-11-05.md` 4장): 설명 대부분이 원본 수집 데이터(`data/ktomok`)에 없는 하중(T-25)·차량 통행 가능/불가·홍보 문구이고, 두께와 어긋나는 문장(80T 이상 블록에 '차량 통행 불가', 60T 블록에 '차량 통행 가능')이 섞여 있다.
- 도구: `scripts/data-quality/build_description_proposals.php`(생성기) + `description_lib.php`(순수 함수), 테스트 `tests/description_proposals.test.php`.

## 2. 정비 원칙

1. **문제 문장이 없는 기존 설명은 바꾸지 않는다**(11개).
2. 문제 문장이 있으면 **그 문장만 뺀다.** 남은 기존 문장은 고쳐 쓰지 않고 순서 그대로 둔다(근거 미확인 — 검토표에 표시).
3. 그 뒤에 **상품 이름·규격에서 읽은 '고르는 기준'**(두께·투수·재질·하중 등급·판매 단위 — 상담 검색 결과와 같은 `ext_selection_guide`)을 항목으로 붙인다. 새 사실을 지어내지 않는다(정해진 틀 문장만).
4. 남는 문장도 기준도 없으면 설명을 비운다(NULL — 상세 화면에서 설명 칸이 숨겨짐).
5. 설명이 없던 상품은 고르는 기준이 있을 때만 채운다(별도 SQL·별도 승인).

## 4. 검증 (로컬, 2026-11-05)

### 4-1. SQL 리허설

임시 스키마(`desc_rehearsal_test`, 운영 조회 결과 1,341행 적재)에서 실행하고 끝난 뒤 지웠다.

- 적용: 정비 680문 + 채우기 121문 → 위 3장 결과와 같음
- 두 번 실행해도 같음(각 문은 정비안을 만든 시점 설명의 MD5 와 같을 때만 바꾼다 → 그 사이 관리자 화면에서 고친 상품은 0행)
- `59_description_revert.sql` 실행 후 원래 설명과 완전히 같음(전체 MD5 비교)

### 4-2. 상품 검색 영향 (설명 칸은 사이트 검색·AI 상품 검색이 함께 찾는다)

`app/bootstrap.php` `search_products()` 는 상품명·규격·**설명**을 함께 찾고, AI 상담 상품 검색(`tool_search_products`)도 같은 함수를 쓴다. 운영 조회 결과로 만든 임시 스키마(`desc_search_test`)에서 분류 이름 245개 + 자주 쓰는 검색어 36개(281개)의 검색 건수를 적용 전후로 비교했다.

처음 안(분류 설명·KS 적용 범위 글을 설명에 넣는 안)은 다른 종류 상품까지 검색돼 버렸다. 그래서 그 두 가지는 생성기 옵션(`--with-category-brief`·`--with-ks-scope`, 기본 꺼짐)으로 돌렸다.

| 검색어 | 지금 | 처음 안(분류 설명+KS+기준) | **최종안(기준만)** |
|---|---:|---:|---:|
| 내구성 | 601 | 0 | 0 |
| 차량 | 648 | 76 | 77 |
| 하중 | 570 | 52 | 52 |
| 주차장 | 80 | 12 | 19 |

- 최종안: 크게 늘어난 검색어 0개. 줄어든 검색어 27개는 대부분 근거 없는 문장으로 걸리던 것이다('우수한'의 '우수', 규사가 '보도블록'·'인터로킹'에 걸리던 것 등).
- **함께 줄어드는 것**: '하수'·'배수'처럼 쓰임새로 찾는 검색은 근거 없는 문장(T-25·홍보와 한 문장)에 같이 있던 쓰임새 낱말이 빠져 덜 찾는다(예: '하수' 검색에 흄관이 빠짐). 반대로 '배수로 덮개'는 1 → 74건(고르는 기준의 그레이팅 덮개 설명).
- AI 상담이 실제로 쓰는 자재 이름 검색어 20개(흄관·PE이중벽관·U형수로관·그레이팅·맨홀·집수정·측구·오수받이·빗물받이·트렌치 등)는 건수가 같거나 1~5건 차이다. 예외는 '인터로킹 블록' 25 → 12, '주차장 블록' 9 → 2 — 근거 없는 용도 문장으로 걸리던 상품이 빠진 것이다.
- 같은 점수끼리의 순서는 실행마다 바뀐다(기존 검색에 동점 정렬 기준이 없음 — 이번 변경과 무관). 그래서 비교는 건수로 했다.

### 4-3. 상세 화면 KS 배지

`public/product.php` 의 KS 배지는 상품명의 KS 표기로만 붙인다. 전에는 설명에 'KS' 글자가 있어도 배지가 붙어, 근거 없는 KS 주장 문장 10개가 인증처럼 보였다.

## 5. 적용 방법 (보류 — 사용자 승인 후)

1. 검토: 검토표 `review.csv`(엑셀)에서 특히 다음을 확인한다.
   - **설명 비움 275개**: 상세 화면에 설명이 없어진다.
   - **남은 기존 문장 405개**: 근거 미확인 문장이다(180개 + 225개).
   - **두께 충돌 12개 상품**.
   빼고 싶은 상품은 알려 주시면 그 상품을 뺀 SQL 을 다시 만든다.
2. 백업: 운영 `products` 의 `id, description` 백업(phpMyAdmin 내보내기)이 먼저다.
3. 정비 적용: `50_description_fix.sql`(680문)을 실행한다. `description` 칸만 바꾸며 가격 칸은 없다.
   - 원격 관리 API 로 할 때: `scripts/tomok db request --tables products --actions update --columns products.description --max-rows 680` → 관리자 화면 승인 → `db stage-sql`.
4. 채우기 적용(따로 승인): `51_description_fill.sql`(121문, `--max-rows 121`).
5. 확인: 상품 상세 몇 개를 열어 본다(설명 없음·항목형 설명). 검색 '차량'·'내구성' 건수가 줄었는지도 본다.
6. 되돌리기: `59_description_revert.sql`. 정비안이 그대로 들어가 있는 상품만 이전 설명으로 돌린다.

생성 파일은 운영 데이터가 들어 있어 저장소 밖에 둔다(생성기가 저장소 안 출력을 거부). 운영 설명이 그 사이 바뀌었으면 다시 조회해 생성기를 다시 돌린다. 이전 설명과 다른 상품은 SQL 이 0행이라 덮어쓰지 않는다.

## 6. 제안 (요청 시)

- **쓰임새 검색 보완**: '하수·배수·우수' 같은 쓰임새 낱말은 검색 동의어(`app/synonyms.php`)로 관 종류(흄관·PE이중벽관·PVC관·수로관)에 잇는 편이 상품 설명 문장보다 정확하다. 검색 설정 변경이라 따로 요청 시 진행한다.
- **상세 화면 국가표준 안내**: KS 적용 범위(사용자 확인분)는 설명 칸에 넣지 않고(검색 영향) 상세 화면에서 상품명 규칙으로 따로 보여 줄 수 있다. AI 상담에는 이미 나온다(검색 결과 basics).
- **로컬 테스트 DB**: 이 세션의 `tomokmall_ai_test` 컨테이너 DB 는 운영 최신 복제본이 아니었다(상품 ID 와 이름이 운영과 다름). 그래서 위 검증은 운영 조회 결과로 만든 임시 스키마로 했다. 운영 복제 스냅샷(`tomokmall_devdb_*.sql.gz`)을 주시면 다음 작업부터 그 DB 로 검증한다.
