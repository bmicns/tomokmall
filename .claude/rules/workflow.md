# 작업 절차·협업 방식 (P1·P3)

> P0 는 `CLAUDE.md` 3장. 이 파일의 어떤 절차도 P0 보다 앞서지 않는다.

## 1. 작업 절차 (모든 작업 공통)
1. **요구사항 확인** — 무엇을, 누가(고객/기업/직원/관리자), 왜. 해결하려는 실제 문제와 목적을 파악한다. 모호하면 추측하지 말고 질문한다.
2. **현황 분석** — 코드를 보지 않고 추측하지 않는다(없는 함수·테이블·컬럼을 가정하지 않음). 관련 파일을 읽고 `grep` 으로 함수·테이블·URL 사용처를 모두 찾는다.
   - 페이지 → `api/*.php` → `app/*.php` 함수 → DB 테이블 순으로 흐름 추적
   - 같은 로직이 여러 곳(고객·관리자 화면, `products_demo_data.php`)에 있는지 확인
3. **등급 판단·계획** — 아래 2장. 계획에는 변경 파일·내용, 영향 받는 기능·화면·권한, 위험(기존 동작·DB·캐시·세션·호환성)과 되돌리는 방법, DB/FTP 작업 필요 여부(필요하면 승인 요청)를 담는다.
4. **구현** — **최소 변경**. 관련 없는 리팩터링·포맷 정리·이름 변경을 섞지 않는다. 기존 코드 스타일을 따른다.
5. **사전 승인** — 되돌리기 어렵거나 외부에 영향을 주는 작업(배포·FTP·운영 DB 는 P0, 그 밖에 파일 대량 삭제·이동, 외부 서비스 호출)은 미리 승인받는다.
6. **기존 기능 보존** — 요청받지 않은 기능·파일·함수·DB 컬럼을 삭제하거나 동작을 바꾸지 않는다. 죽은 코드로 보여도 사용처가 없다는 근거와 함께 **제안만** 한다.
7. **검증** — 3장. **커밋·푸시** — 5장. **보고** — 6장.

## 2. 작업 등급과 진행
| 등급 | 대상 | 진행 |
|---|---|---|
| **A 즉시** | 오타·문구, 원인이 분명한 버그, 이미 합의된 작업의 후속, 기록 문서 | 1~3줄 계획 → 구현 → 검증 → 커밋 → 보고. 토론 없이 신속하게 |
| **B 짧은 확인** | 한 화면·한 기능 범위, 방법이 여럿이지만 되돌리기 쉬운 것 | 권장안으로 진행하고 보고에 "다른 방법: …" 한 줄 |
| **C 토론** | DB 구조, 아키텍처, 가격·권한·주문 흐름, 주요 UI/UX, 새 라이브러리·프레임워크·빌드 도구, 여러 화면 영향, 데이터·분류 규칙, 규칙 파일, 관련 없는 대규모 리팩터링 | 아래 형식으로 제안 → **사용자 결정 전에는 구현하지 않는다** |

- 등급이 애매하면 높은 쪽. 작업 중 C 성격이 드러나면 멈추고 보고한다.
- **C등급 답변 형식**: ① 문제 및 목표 ② 실무 개발자 관점(숙련된 개발자라면 어떻게 하는지) ③ 대안 비교 2~3개(장단점) ④ 최종 추천 1개(유지보수·확장성·성능·데이터 안정성·개발 비용 종합) ⑤ 실행 여부(사용자 결정 사항·이후 계획)
- **스스로 점검**: 정말 최선인가 / 더 단순하고 안정적인 방법은 없는가 / 기존 시스템·확정 결정과 충돌하지 않는가 / 장기 유지보수에 유리한가 / 데이터 안정성·기존 기능에 영향은 없는가
- 사용자 제안이 기술적으로 비효율적이거나 더 나은 대안이 있으면 동의만 하지 말고 근거를 들어 다른 방향을 제안한다. 최종 결정은 사용자.
- **고정 전제**: 닷홈 공유호스팅, PHP 8.4·MySQL 8.0, 프레임워크 없음, FTP·원격 관리 API 배포, 1인 운영. 이 전제를 깨는 제안(프레임워크·CI 배포·컨테이너 운영 등)은 대안 비교에만 넣고 근거를 단다.
- **재논의 원칙**: `data-decisions.md` 의 결정은 새 근거(데이터·오류·요구 변화)가 있을 때만 다시 논의를 제안한다.

## 3. 테스트·검증
```bash
php -l <변경한 파일>      # 또는 전체: find public app -name "*.php" -print0 | xargs -0 -n1 php -l | grep -v "No syntax errors"
php tests/functions.test.php   # 단위 테스트(DB 불필요)
bash scripts/local-up.sh       # 로컬 서버 http://localhost:8080 (또는 docker compose up — 웹 :8080, phpMyAdmin :8081, MySQL :3307)
bash scripts/smoke.sh http://localhost:8080   # 인자 없이 실행 금지(기본 대상 = 운영)
```
- 버그 수정은 **재현 → 수정 → 같은 방법으로 해결 확인**. 순수 함수(검색 분해·수량·가격 계산·파싱)를 바꾸면 `tests/functions.test.php` 에 회귀 테스트를 추가한다.
- 화면 변경은 로컬에서 직접 열어 확인하고 권한별(비로그인/고객/기업/직원/관리자) 영향을 본다.
- 실제 데이터가 필요한 기능은 운영 복제 개발 DB 로 검증한다(`database.md` 5장). 기존 자동화 테스트·검증 스크립트는 그대로 유지한다.
- AI 가 생성한 코드도 사람이 쓴 코드처럼 리뷰·테스트한다. 특히 SQL, 권한 검사, 가격 계산.
- 테스트를 실행할 수 없으면 그 사실과 이유를 보고한다. **실행하지 않은 테스트를 통과했다고 말하지 않는다.**
- **보안 핵심(모든 PHP)**: Prepared Statement 만 사용, 출력은 `htmlspecialchars($v, ENT_QUOTES)`, API 마다 권한 함수 + 소유자 확인. 상세 `php-backend.md`.

## 4. 오류 발견·수정
1. 증상 기록: URL/화면, 권한, 입력, 기대 vs 실제, 오류 메시지 → 2. 로컬에서 같은 조건으로 재현
3. 원인 추적: 페이지 → API → app 함수 → DB, 로그·응답·쿼리, 브라우저 개발자도구(Network/Console)
4. **근본 원인**을 고친다. 오류 무시·`@` 연산자·빈 catch 로 증상만 가리지 않는다.
5. 같은 패턴의 버그가 다른 곳에도 있으면 **보고**한다(요청 범위 밖이면 고치지 않고 제안).

## 5. Git 커밋·푸시 (작업 브랜치)
- 커밋은 **하나의 목적** 단위로 작게, 메시지는 한국어로 "무엇을 왜". 예: `견적: 수량 0 입력 시 총액 NaN 표시 오류 수정`
- 다음을 **모두** 만족하면 별도 승인 없이 **작업 브랜치에** 커밋·푸시한다(`main` 은 P0-1):
  1. 필수 테스트(문법 검사·관련 단위 테스트·로컬 테스트 DB 가 있으면 통합 테스트·가능한 기능 확인) 통과, 해결 안 된 오류 없음
  2. `git status`/`git diff` 에 요청 범위의 변경만 있음(무관한 수정·임시 파일·`.env*`·로그·업로드·대용량 덤프 없음)
  3. 시크릿 패턴 검사 통과: `git diff --cached | grep -iE "pass|secret|api_key|token|sk-"`
  4. 원격 브랜치와 충돌 없음(푸시 전 `git fetch`, 원격이 앞서 있으면 보고)
- 하나라도 어긋나면(테스트 실패·오류·예상치 못한 변경·충돌) **커밋·푸시하지 않고** 먼저 보고한다. 사용자가 "커밋·푸시하지 마세요"라고 하면 그 지시가 우선한다. 승인 범위 밖 변경은 커밋에서 빼고 보고한다.
- 커밋·푸시 후 브랜치명·커밋 해시·변경 파일·테스트 결과를 보고하고 **`main` 병합 승인을 요청**한다. 승인 후 병합·푸시하고 병합 커밋 해시를 보고한다.

## 6. 보고
- 변경 파일, 실행한 테스트 명령과 결과(실패 포함), 커밋 해시·푸시 결과, 남은 위험·후속 작업, **사용자가 해야 할 일**(배포·DB 반영 등).
- 하지 못한 검증은 "하지 못했다"고 밝힌다. UI 변경은 데스크톱·태블릿·모바일 확인 결과를 구분해 적는다.
